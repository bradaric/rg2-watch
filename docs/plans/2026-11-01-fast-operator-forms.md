# Fast Operator Forms Implementation Plan

> **For agentic workers:** REQUIRED: Use subagent-driven-development (if subagents available) or executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show all changed operator forms in roughly ten seconds without rebuilding every form, while leaving the unofficial tally on its existing background cadence and retiring operator `file://` support.

**Architecture:** A bounded, transactionally maintained SQLite station-change journal powers a localhost-only, read-only, revisioned feed with a generation token on every response. The server builds operator form rows only for affected groups; the browser applies those rows by tagged identity, marks tally-dependent cells “Updating,” and merges full tally snapshots captured by a dedicated consistent SQLite read transaction without rolling back newer rows. All full-snapshot writers share one cross-process lock. First load serves immediately, bootstrapping rows in pages if necessary. `export-results` remains an independent, manually generated, self-contained public HTML page.

**Tech Stack:** Python 3.12, SQLite/WAL, `http.server`, existing vanilla JavaScript/DataTables, pytest, existing `rg2watch` CLI.

---

## Scope, constraints and existing state

- Approved behavior: HTTP-only operator page; all form-related changes (documents including moves/removals, analyses, findings, verdicts, corrections, classification and decision changes); approximately 10-second target, not a guarantee; “Updating” in Numbers and Result inclusion until a matching tally rebuild; keep current full-build cadence initially; prompt `view.sh`/`serve` startup, including an empty-state loading page; bounded change history with browser rebootstrap on expiry.
- Existing architecture: `src/rg2watch/browse.py:build_data` performs a whole-election read, row construction and `build_tally(... include_station_results=True)`, and `build_page` writes `data.json`, `data.js` and metadata. `src/rg2watch/cli.py:_watch` runs that builder in a daemon thread with `browse_interval_s=120` (delay **after** each build); `view.sh` calls blocking `rg2watch browse` before `serve`; `serve` itself blocks on `build_page` if `data.json` is absent. `src/rg2watch/static/index.html:applyData` clears/re-adds all DataTable rows; correction and type-13 paths currently poll the full snapshot. `src/rg2watch/server.py` does not serve `data.js`/`status.js`. `public_results.py` calls `build_tally` directly and is out of scope.
- The working tree at planning time already contains **unstaged** edits to `src/rg2watch/store.py`, `src/rg2watch/browse.py`, `tests/test_store.py`, `tests/test_browse.py` for a separate BM 6/8 reassignment bug. Preserve them, do not erase/rewrite them as this feature, and coordinate with the operator before any live watcher restart, migration, backup, or production DB mutation. Do not assume this plan authorizes deployment.
- Do **not** solve the performance problem by calling `build_data()` or whole-election `build_tally()` from the feed or by shipping all rows on every poll. Public-results output, privacy, localhost binding, anti-cross-site protections and verdict/correction semantics must not regress.
- Stage development with verifiable fallbacks: (1) instrument and retain existing full snapshot while removing unused `.js` twins; (2) journal and selective endpoint can be tested without switching the browser; (3) switch the browser to feed with a visible “reconnecting” state and a manual full-data reload fallback; (4) enable nonblocking startup once feed/bootstrap and tally-version races pass. Do not deploy half the protocol or rely on a stale tally without a visible warning. Keep the existing complete `data.json` available as recovery even after the feed becomes primary.

## File map and interfaces

- Create `src/rg2watch/operator_feed.py`: bounded batch/bootstrap protocol and selective station-row assembly; keep it independent of HTTP. Extract reusable pure row/version/group helpers from `browse.py` as needed, rather than duplicating incompatible presentation rules.
- Modify `src/rg2watch/store.py`: migrate/create persistent journal, stable database instance UUID, and indexes; atomic group invalidation for all relevant writers, revision/floor queries, paged group/document/analysis/finding reads; add a read-only snapshot connection mode which skips schema creation/migrations, starts a SQLite read transaction, and closes it after the full build. Keep migration idempotent on old election DBs and in-memory tests. Avoid hot-path journal entries for `findings.alerted_at` and other non-operator-visible writes.
- Modify `src/rg2watch/browse.py`: reuse shared form-row serializer for full and selective builds; capture the high-water revision **inside the same dedicated read transaction before any data reads**, then build both rows and tally through that connection; write the resulting revision with both while preserving the existing public data shape where possible. Write only JSON operator snapshots and metadata; add phase timings. Publish data and metadata as a version-matched pair (the browser rejects mismatches). Never label a mixed-state build with a revision.
- Modify `src/rg2watch/server.py`: strict same-origin `GET /operator-feed?parent=<id>&since=<revision>` and `GET /operator-bootstrap?parent=<id>&cursor=<...>` routes through a supplied read-only handler; validate input, payload bounds and response headers. Never expose SQLite paths, credentials or unallowlisted files.
- Modify `src/rg2watch/cli.py`, `scripts/view.sh`: wire feed in both `watch` and `serve`; stop blocking `view.sh`/`serve` on the full build; refresh **missing and stale** snapshots in the background, with one builder per DB/page directory and clean shutdown. Route manual `rg2watch browse` and all final/correction-triggered snapshot writes through that same lock; manual browse exits promptly with an explicit busy error when held.
- Modify `src/rg2watch/static/index.html`: HTTP-only startup, paged bootstrap and periodic revisions; keyed DataTables replacement/removal preserving filters, sorting, paging, selected form and open child rows; independent tally refresh and stale-cell handling; change-aware correction/type-13 refresh.
- Modify `docs/review-and-sharing.md`, `docs/reference.md`, `docs/runbook.md`, `README.md` as applicable: remove operator direct-file instructions, document startup/loading, feed/tally timestamps, latency expectations and recovery. Do not alter the self-contained public export contract.
- Tests: `tests/test_store.py`, `tests/test_browse.py`, `tests/test_server.py`, `tests/test_status_cli.py`, `tests/test_review.py`, `tests/test_operator_corrections.py`, `tests/test_type13.py`, `tests/test_public_results.py`, plus a new focused `tests/test_operator_feed.py` and real-browser/Node harness tests where existing browser tests live.

## Chunk 2: Durable, bounded station-change tracking

### Task 3: Transactional journal and recovery protocol

- [ ] Test first on fresh, migrated and in-memory Stores: repeat opening is idempotent, aborted writes emit no revision, monotonic revisions survive restart, no-op updates do not notify, a move records **both old and new tagged group identities**, pruning retains a durable floor, stale `since` and invalid/future revisions request rebootstrap. Include different election parents and two distinct NULL-`station_key` documents, plus removal, replacement and reassignment of each; preserve minority/council grouping.
- [ ] Define one canonical identity used by journal, bootstrap, feed, tombstones and browser: for a non-NULL key, `(parent, "station", station_key)`; for a NULL key, `(parent, "document", document_id)`. A form row adds `doc_type` to that group identity; in the unlikely NULL-key/NULL-type case the document ID still disambiguates it. A NULL-key document reassigned to a station emits a tombstone for `document:<id>` and invalidates `station:<key>`; reverse reassignment invalidates both too. Do not treat NULL as the literal station name "None" or coalesce all NULL-key documents. `browse.py:225-227` already groups NULL keys by document ID; preserve that behavior.
- [ ] Create a persistent monotonic `operator_feed_revision` counter (not `MAX(journal.id)` alone, which may be reused after pruning), a stable random DB-instance UUID initialized once during migration, and `operator_feed_changes(revision, parent, group_kind, group_key)` with indexes `(parent, revision)` and keyed pagination; use a stringified document ID for document groups. Every invalidation must be in the **same transaction** as its data change; look up old group before update, log both old/new on reassignment. Use a single, documented invalidation helper in Store writers where possible; if using SQLite triggers, explicitly avoid recursive journaling and verify all writers, including SQL bulk updates, are covered. Never journal `mark_alerted`, spend-only records or status clocks. Bound retained revisions by fixed revision window (suggest initial 10,000 revisions per election, adjusted by benchmark); persist the oldest valid `since`/floor independently of pruning, and cap batch size (suggest 200 distinct groups); return `reset_required` rather than silently truncating unseen changes.
- [ ] Test invalidation for document add/replacement/removal/reassignment, analysis status/report and model choice, findings insert/update/delete, reviews, operator/type-13 correction/revoke/target change, classification override and RG-7/8/9 changes impacting linked RG-2 rows. For legacy/multiple station-key references, invalidate the **actual selected target** and old target when ownership changes. Verify no missing invalidation across process restart, multi-Store writers, failed transaction and pruning during polling.
- [ ] Persist a **global-reset journal entry** when the preferred fallback model ordering changes due to newly completed/removed analyses (coverage ordering in `analysis_selection.py:5-24` can affect unrelated stations). The feed returns `reset_required` for a global entry rather than attempting to enumerate all rows. This is separate from the generation token for non-journal inputs (next task); test that an unrelated station does not silently keep its former preferred model.

### Task 5: Bounded feed and paged bootstrap endpoints

- [ ] Test first: changing effective model or a relevant config threshold/list/tally-scope setting without writing to SQLite, replacing code/template rules between server restarts, using a different DB with the same numeric revision, and restoring an older DB backup all force reset/rebootstrap on the next **empty** feed response. Test unchanged token on an ordinary empty poll and snapshot/token disagreement. Verify no token input/preimage containing secrets is returned.
- [ ] Define one deterministic generation token `sha256(canonical_json(inputs))` for each `(database, election)` across watcher, standalone serve, bootstrap and snapshot writers. Inputs: persistent DB-instance UUID (not path/stem), election ID and schema/protocol version, effective configured model and **all operator presentation/tally-affecting config fields** (at least `list_names`, `tally_scope`, rule thresholds and correction/model-selection settings from `Config`), election metadata affecting labels/URLs, and a digest of operator implementation/template resources (`src/rg2watch/*.py` and `static/index.html` plus vendored page assets) computed once at startup. Exclude API keys, ntfy topics, OAuth files, file paths and unrelated operational secrets; hash the canonical serialized values, never return the preimage. Recompute config/election metadata inputs when loading a new process; if relevant settings are mutated in-process, recompute before responding. Document and test a whitelist of config fields plus an assertion that any newly introduced config field is reviewed for token impact rather than silently omitted. A different running process with incompatible token must not overwrite another process's `data.json` even if it holds the builder lock: fail visibly or serve without publishing until settings agree.
- [ ] Test first: strict local Host/Sec-Fetch-Site restrictions and existing GET/HEAD protections also apply to new routes; unknown/invalid election/revision/cursor returns 400/404, not a traceback; no write methods or RIK calls are invoked; huge responses are bounded; no form of path traversal or raw SQL access. Preserve gzip behavior and CSP. A stationary poll yields a small empty response.
- [ ] Protocol: `GET /operator-feed?parent=P&since=R` returns `{db,parent,generation,revision,through,more,reset_required,groups:[{kind,key,rows}],tombstones:[{kind,key}]}`; **always include generation even for an empty feed**. Browser compares it to the generation received from bootstrap or `data.json` **before** accepting `through` or applying rows. On mismatch: discard current form/tally data, visibly enter loading/reconnecting state, and rebootstrap; do not just advance the cursor. `revision` is the current durable high-water; `through` is the highest fully consumed journal revision; never advance client cursor past unreturned changes. Deduplicate tagged group identities only **after** selecting a bounded revision range; repeated keys across chunks are safe. Return `reset_required` if `since < floor`, `since > revision`, DB/parent/schema token mismatch, or snapshot generation is incompatible. Capture a consistent SQLite read view for journal high-water and selected group rows (or read high-water both before/after and retry); no DB lock held during expensive JSON serialization.
- [ ] Bootstrap: `GET /operator-bootstrap?parent=P&cursor=C` streams bounded pages of grouped rows in deterministic tagged-group order, with a fixed bootstrap high-water captured when bootstrap starts; every page returns `generation` and rejects a cursor whose generation differs. Use an opaque, validated cursor/token, not client-supplied SQL. If changes occur during bootstrap, finish pages then replay journal entries after that high-water before declaring caught up. If journal floor overtakes it or DB identity changes, restart bootstrap and show a visible retry state. First page also supplies election title, document type/rule metadata and version. Design page size by **number of rows and response bytes**; make it configurable only if benchmark requires it.
- [ ] Wire read-only handler into `_start_web` for `watch` and `serve` and close owned resources at shutdown. Provide a controlled global invalidation response for changed list-name/config/model selection whose effect cannot be localized. Verify an election-sized simulated DB feed queries O(changed stations) and stays bounded with a concurrent watcher; benchmark local handler p50/p95 without any RIK or AI calls.

If the builder fails, serve/feed remain usable and display stale-tally warning; no duplicate builders with concurrent watcher/serve. Test clean stop and process restart, including feeds that are between bootstrap pages. Race a manual browse against watcher, serve, final `--until-done` and correction-triggered full builds; assert one writer and monotonic snapshot revision.
- [ ] Keep `copy_static` cheap; remove synchronous build from `_cmd_serve`. **Every** `build_page` writer of the same DB/page directory acquires the **same per-DB/page cross-process builder lock**, including `_cmd_browse`, watch background, standalone serve, final `--until-done`, and correction/classification-triggered full builds. Lock covers opening the read snapshot through publishing both data and metadata; acquire before starting a snapshot so a later-started build cannot publish an older version after a newer one. Manual `rg2watch browse` uses nonblocking acquisition: on busy, print `operator snapshot build already running; try again later` to stderr and exit nonzero without touching the files. Background builds skip on busy, log and retry at the next scheduled interval; a final `--until-done` build skips with a visible warning rather than waiting indefinitely. Only the lock owner publishes; failed builds back off and expose a stale-tally warning rather than hot-looping. Standalone serve schedules a build when snapshot is missing, corrupt, metadata- or generation-mismatched or its revision is behind journal high-water; if new revisions arrive while standalone serve remains open, repeat at the existing `browse_interval_s` cadence (not on every feed poll). Release lock on errors/shutdown. `scripts/view.sh` should only validate DB and launch `serve`; retain `rg2watch browse` as a manual full-build command. Ensure the first watcher page is served before its first expensive build and loader can bootstrap regardless of tally availability.
