# Viber Case Handoff Implementation Plan

> **For agentic workers:** REQUIRED: Use subagent-driven-development (if subagents available) or executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the operator publish a human-escalated, already-cached document version as a publicly viewable, case-specific Google Drive folder and copy a Serbian Cyrillic Viber handoff message, without automatically contacting recipients.

**Architecture:** Keep the existing loopback-only review UI and SQLite database. A separate preparation request builds an editable, AI-assisted Cyrillic draft from the review note; an explicit Publish request freezes the edited text and cached PDF, then creates/uploads a private Drive case folder and makes only that folder link-viewable after both files exist. A per-URL cross-process lock serializes attempts; a brief shared review/publication decision lock makes the final verdict check and public-sharing request one ordered operation. Network uploads run outside the watcher/store lock and off the HTTP handler thread. No RIK fetch is part of publication.

**Tech Stack:** Python 3.12, SQLite, existing Anthropic SDK, Google OAuth installed-app flow and Drive API client, vanilla JS in the existing static page, pytest with fakes (no live Google/Anthropic calls in tests).

---

## Agreed boundaries and decisions

- This is a **manual, one-case-at-a-time handoff** to observers/controllers. `escalate` is not Publish; no Viber or Instagram API, automatic send, public browse server, bulk publishing, correction UI, or background publishing queue.
- Sign in using the operator's own Google account; a dedicated service account is out of scope. OAuth scope is limited to files/folders created by the app (`drive.file`). An initial local authorization/setup step is acceptable; it must not happen implicitly on an HTTP request. Secrets and tokens stay local and untracked.
- Public access applies to **one approved case folder**, not the user's working/root Drive folder. The exact sharing setting is Drive `anyone` / `reader`, set only after uploads complete. Anyone who receives or forwards that folder link may open it; describe that plainly in the UI.
- Folder contents: one UTF-8 Serbian Cyrillic case explanation file (plain text is sufficient for the initial handoff) and the exact locally cached PDF for the reviewed URL. The case text includes election, municipality/station, document version URL, RIK link, a human-edited concern with cautious attribution, and a SHA-256 **of the PDF bytes**. Do not confuse that with the existing URL-hash cache filename. Do not assert a retrieval timestamp the app did not record; `first_seen_at` and RIK upload time are different concepts. Never publish internal review notes directly or expose raw analysis reports.
- The internal note can seed an AI draft, but the operator must be able to edit it and must explicitly confirm Publish. Draft failure (no key, cap reached, API failure, etc.) must leave a manually editable blank/template summary and cannot cause publication. Drafting calls consume the **existing per-election analysis spend cap**; no independent uncapped drafting budget. Keep the existing cap's best-effort concurrency semantics explicit rather than claiming strict prevention of in-flight overspend.
- A **new** Publish is blocked when the exact version has no cached local PDF; never fetch a replacement from RIK. Also block an unknown URL, a non-`escalate` latest verdict, an empty public summary, an unconfigured Drive account, or publication already in progress. Older escalated versions remain independently eligible: always key by document URL, not the currently displayed station row. Existing completed publication is returned **before** new-publication eligibility checks, even if a later verdict on that URL is `ok`/`unsure` or a correction document is accepted. A changed verdict does not revoke or silently alter a case that already did its job.
- One published link per document URL. Before any remote creation, freeze the approved summary and exact local PDF bytes in a private local staging file and persist their content hashes. Retry with changed text/PDF refuses and asks the operator to inspect the frozen pending package; this version has no replace/abort workflow. A repeat after completion returns the stored link/message, not a new public case or rewritten summary. Google-assigned IDs are pre-generated and persisted *before* create calls, so an uncertain response/crash is retried against the same IDs. If publication fails before sharing, the folder stays restricted; a later explicit retry reconciles it. No first-version correction workflow: later edits/notification are manual and out of scope.
- `watch` and `serve` can coexist on the same SQLite file. A unique URL constraint and an in-process worker guard alone do **not** serialize remote operations. Use OS `flock` on a stable per-database/per-URL file next to the DB, held throughout one publish attempt (including recovery and permission reconciliation). An active owner causes a fast “in progress” response; after a crash the OS releases its lock, and the next explicit Publish safely reclaims the persisted pending state. This assumes both processes use the same local SQLite database/filesystem; do not claim multi-host/NFS coordination.
- For the final public permission only, `set_review` and the publishing worker acquire a separate per-URL **decision** file lock. The worker takes it, reads the newest review under a DB transaction, requests/inspects Drive `anyone` permission while holding this decision lock, and records the public state before releasing it. `set_review` takes the same lock before recording a changed verdict; CLI and server both call that Store method. Thus an `ok` saved first prevents sharing; an `ok` saved afterward does not undo an already public case. Do not hold a SQLite transaction/Store mutex across the Drive request; the decision lock serializes just that URL, not the watch loop. Lock order: publish lock then decision lock, never the reverse. On a crash after remote permission succeeds but before DB commit, the next attempt checks the preassigned folder ID and permission before applying a new verdict check: it records that already-public historical case without undoing it.

## Existing code and integration map

- `src/rg2watch/fetch.py`: `fetch_pdf` caches `sha256(url).pdf`; analysis uses it in `pipeline.py:244-254`, but review can happen without analysis or a local PDF.
- `src/rg2watch/store.py`: `reviews` history, `latest_reviews`, and `total_spend`; SQLite connection is shared behind a lock. `documents.url` identifies a version. Add narrowly scoped publication/drafting-cost persistence here; keep Drive calls out of store methods.
- `src/rg2watch/browse.py`: `record_review`, `reviews_payload`, `build_data` and `Local PDF` presence; reuse document metadata without making the public case depend on stale `data.json`.
- `src/rg2watch/server.py`: loopback-only server, strict Host/Origin/Fetch-Site checks for POST `/review`, allow-listed GETs. Add only explicit local preparation/publication routes and reuse the same request protections; do **not** bind publicly or serve OAuth tokens.
- `src/rg2watch/cli.py`: both `watch` and `serve` wire `_start_web`; create the publishing service in both cases so `serve` works even when watching is stopped. No Google/AI credentials needed to start the watcher; failures affect this optional feature only.
- `src/rg2watch/static/index.html`: version-specific `reviewBox`, `submitReview`, and live `reviews.json`. Put the controls beside the relevant version, including a previously escalated version in an older-version row; show link/message after success and a clear local-PDF/config/error state.
- `src/rg2watch/config.py`, `rg2watch.example.toml`, `.gitignore`, `README.md`, `pyproject.toml`/`uv.lock`: configuration, safe local credential paths, setup instructions and dependencies. Keep credentials out of the repo and out of `data.js`, `status.json`, responses, and logs.

## Acceptance checks

1. A latest `escalate` verdict and saved PDF are required to **start a new** publication; previous versions are handled by exact URL. No cached copy means no new Publish, even if RIK is reachable. A later verdict change never silently removes an already published case.
2. An explicit preparation click yields editable Serbian Cyrillic draft (or a manual template if unavailable), with a paid call reflected in the same per-election cap. No AI text reaches Drive before the operator explicitly clicks Publish.
3. Publish makes only the case-specific Drive folder link-readable after the checked PDF and public text are present; operator gets the stable link and copyable Cyrillic Viber message. No message is sent by the app.
4. Repeated clicks, separate `watch`/`serve` processes, server restarts, and partial Drive failures do not make a second public case or accidentally publicize an incomplete one. Changed retry inputs cannot replace frozen summary/PDF. Review-versus-share ordering is deterministic. The watch loop and local review server remain usable if publication fails.
5. Existing local-only server, review history, spend/status reporting, and browse behavior remain intact.
